# Milepost Backend Configuration

## Local development

Activate the `local` Spring profile explicitly to use local-only fallback settings. Run from this directory with Java 21 and Maven:

```powershell
$env:SPRING_PROFILES_ACTIVE = 'local'
.\mvnw.cmd spring-boot:run
```

If startup reports `Could not resolve placeholder 'app.jwt.secret'`, the `local` profile was not active in the process that launched Spring Boot. For an IDE launch, set `SPRING_PROFILES_ACTIVE=local` in that run configuration. The application intentionally has no implicit local profile: do not add a local default to `application.properties`, because deployments must explicitly activate `prod` and must not load local fallback settings.

The local profile preserves the existing PostgreSQL, JWT, administrator bootstrap, CORS, Hibernate update, and Flyway settings in `src/main/resources/application-local.properties`. You can override local values with environment variables. Local fallback credentials and the local signing key are for development only and must never be reused in production.

The frontend uses same-origin `/api` requests in production. For local development, configure `VITE_API_BASE_URL` in `frontend/.env.development` if the backend is not reachable through the default development setup.

## Production profile

Activate production with `SPRING_PROFILES_ACTIVE=prod` as the only active Spring profile. There is no implicit local default profile; if a profile is omitted, local fallbacks are not loaded. Production settings have no usable database, JWT, or CORS fallbacks. The application validates them before creating a datasource or running Flyway. Validation errors name the missing or invalid setting, never its value.

Required environment variables:

| Variable | Purpose |
|---|---|
| `SPRING_PROFILES_ACTIVE` | Set to `prod`. |
| `DB_URL` | PostgreSQL JDBC URL, including host and database name. |
| `DB_USERNAME` | Database account. |
| `DB_PASSWORD` | Database account password. |
| `JWT_SECRET` | Base64 encoding of at least 32 randomly generated bytes. Generate with `openssl rand -base64 48`; store in a deployment secret manager. |
| `CORS_ALLOWED_ORIGINS` | Comma-separated, exact HTTPS origins, with no paths or wildcard. Supply the real frontend origin; none is assumed here. |

`JWT_EXPIRATION_MS` is optional and defaults to one hour. Never put database credentials, JWT keys, or administrator passwords in `VITE_*` variables; Vite embeds those values in browser-accessible assets.

Example PowerShell environment setup (replace placeholders in your deployment system; do not commit these values):

```powershell
$env:SPRING_PROFILES_ACTIVE = 'prod'
$env:DB_URL = 'jdbc:postgresql://<database-host>:5432/<database-name>'
$env:DB_USERNAME = '<database-user>'
$env:DB_PASSWORD = '<database-password>'
$env:JWT_SECRET = '<Base64-encoded-random-secret>'
$env:CORS_ALLOWED_ORIGINS = 'https://<your-frontend-origin>'
```

Production CORS accepts only explicit HTTPS origins. Do not use `*`, localhost, or a path in a production origin. Terminate HTTPS at the production ingress or web server.

## Administrator provisioning and rotation

Administrator bootstrap is disabled by default in production. For a deliberate first-time bootstrap, set `APP_ADMIN_BOOTSTRAP_ENABLED=true`, `APP_ADMIN_EMAIL`, and `APP_ADMIN_PASSWORD` in the deployment secret store. The password must have at least 16 characters. Start the application once, then remove the password from the deployment environment and return the bootstrap flag to `false`.

If the email already belongs to an administrator, bootstrap leaves that account unchanged. To intentionally rotate that account's password, set `APP_ADMIN_BOOTSTRAP_ENABLED=true` and `APP_ADMIN_ROTATE_EXISTING=true`, provide the existing administrator email and new password, and start once during a controlled maintenance window. Rotation fails if the account does not already exist; the seeder refuses to change a non-admin account. The lookup and save run in one transaction, though a transaction cannot undo work committed by an earlier operation. Immediately disable both flags and remove the bootstrap password afterward. Do not leave rotation enabled for routine restarts.

## Schema and migrations

Production sets `spring.jpa.hibernate.ddl-auto=validate`. Hibernate will refuse startup if the schema does not match the entity mappings. This repository contains Flyway migrations V1 and V2; their compatibility with an existing production schema and migration history has **not** been verified here.

Flyway is disabled in the production profile by default. Do not set `FLYWAY_ENABLED=true` for an existing database until its schema and `flyway_schema_history` have been reviewed, a backup is available, and the migrations have been rehearsed against a disposable copy. Production also disables automatic baselining. An existing non-empty schema without Flyway history requires an explicitly reviewed baseline procedure; do not guess a baseline version or run migrations against an unverified database.

For a new disposable database, migrations can be run by starting the application with `FLYWAY_ENABLED=true`; Hibernate validation then checks the result. For production changes, rehearse that process on a disposable PostgreSQL database first, take a verified backup, and follow the deployment team's approved migration and rollback procedure. A database restore may be required to roll back schema changes; application rollback alone may not be sufficient.

## Frontend production API URL

The frontend reads `VITE_API_BASE_URL` at build time. Leave it unset or empty when the production web server proxies `/api/**` to Spring Boot on the same origin. Set it to the actual API origin only when the API is hosted separately, and configure that exact frontend origin in `CORS_ALLOWED_ORIGINS`. No production domain is configured in this repository.

Serve the built frontend with a history fallback to `index.html` for application routes, and route `/api/**` to Spring Boot before applying that fallback. See `frontend/README.md` for an Nginx example.
